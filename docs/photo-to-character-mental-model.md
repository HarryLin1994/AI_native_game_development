# Photo-to-Character Mental Model

This document defines the working model for the first major system: real photo to generated fictional battle character. The goal is to keep the MVP local, understandable, and easy to split into deeper modules later.

## Current Goal

Build a consent-based local MVP that can:

1. Accept a Source Photo from upload or camera.
2. Extract non-identifying Photo Signal.
3. Ask the player for creative direction.
4. Produce a deterministic Character Spec.
5. Generate a Retouched Portrait and Card Cover.
6. Save a playable Battle Card.
7. Run a small Battle Test against a CPU opponent.

## Non-Goals

- No person identity recognition.
- No claim that the system detects real age, gender, ethnicity, emotion, health, personality, or social status.
- No server-authoritative multiplayer yet.
- No account system yet.
- No economy, trading, or rarity monetization yet.

## Inputs

**Source Photo**

- Comes from file upload or camera capture.
- Should be treated as sensitive.
- Gives visual composition, palette, and broad creative reference.

**Text Seed**

- Short optional text from manual entry now.
- Later this can come from a real OCR adapter.
- It should influence motifs, names, or symbols, not identity claims.

**Generation Profile**

- Age Impression: fictional age direction.
- Real-World Role: declared job, hobby, or identity motif.
- Visible Traits: short tags like glasses, short hair, calm, sporty, black jacket.
- User-Supplied Context: optional background, preferences, values, or identity details supplied with consent.
- Combat Style: player-chosen battle preference.
- Card Mood: art direction.
- Image Mode: local preview or AI retouch.

**Capture Context**

- Optional time, approximate location, weather, and place type.
- Should use coarse creative labels by default, not exact tracking data.
- If missing, the generator uses Default Generation Template values.

**Reroll Seed**

- Changes output variation while keeping the same source inputs.
- Should affect names, secondary flavor, and visual composition more than core identity.

**Generator Config**

- Model choice, image quality, local or AI mode, and future safety limits.
- This should be adapter-owned, not spread through the character rules.

## Core Outputs

**Photo Analysis**

Intermediate non-identifying signal:

```json
{
  "metrics": {
    "brightness": 0.52,
    "contrast": 0.61,
    "saturation": 0.47,
    "edgeDensity": 0.39,
    "centerFocus": 0.68,
    "symmetry": 0.57,
    "textSignal": 0.2
  },
  "palette": [{ "hex": "#556a7b", "label": "Cool", "weight": 0.31 }],
  "textSeed": "A12",
  "hash": "stable-analysis-hash"
}
```

**Character Spec**

The canonical generated character. This is the most important output because battle, progression, save/load, UI rendering, and card art should all depend on it.

```json
{
  "schema": "photo-character-lab.character.v1",
  "source": "real_photo_local_analysis",
  "identityPolicy": "no_identity_recognition",
  "generationProfile": {},
  "name": "A12的焰行者",
  "className": "焰行者",
  "element": "Ember",
  "rarity": "R",
  "appearance": {},
  "personality": {},
  "combatRole": {},
  "traits": ["Ember", "中心壓制"],
  "stats": {
    "power": 72,
    "speed": 51,
    "guard": 44,
    "focus": 58,
    "luck": 33
  },
  "skills": []
}
```

**Retouched Portrait**

- A fantasy portrait derived from the Source Photo.
- Can be generated by local canvas or an AI image adapter.
- Should preserve broad visible cues without claiming identity recognition.

**Card Cover**

- The final 2D card presentation.
- Should be reproducible from Character Spec, Retouched Portrait, and card layout rules.

**Battle Card**

- A saved playable object.
- Combines Character Spec, Card Cover, level, XP, wins, and losses.
- Shows a Card Stat Line such as HP, ATK, DEF, COST, and Level.
- Should be usable in Battle Test without needing the Source Photo.

## Pipeline

```text
Source Photo
  -> normalize image
  -> Photo Signal Analyzer
  -> Photo Analysis

Generation Profile + Photo Analysis + Reroll Seed
  -> Character Generator
  -> Character Spec

Source Photo + Character Spec
  -> Visual Generator
  -> Retouched Portrait
  -> Card Cover

Character Spec + Card Cover + progression defaults
  -> Battle Card
  -> Card Stat Line
  -> Character Library
  -> Battle Test
```

## Big Modules

### Capture Module

Interface:

```ts
captureSourcePhoto(input): Promise<SourcePhoto>
```

Responsibilities:

- Accept file upload or camera frame.
- Normalize image dimensions and format.
- Own browser permission concerns.

Keep out:

- Character rules.
- Battle rules.
- AI image generation.

### Photo Signal Analyzer

Interface:

```ts
analyzePhoto(sourcePhoto, textSeed): Promise<PhotoAnalysis>
```

Responsibilities:

- Extract non-identifying Photo Signal.
- Produce stable metrics and palette.
- Accept Text Seed.

Future adapters:

- Canvas analyzer for local MVP.
- OCR adapter for real text extraction.
- Vision model adapter only if we keep strict consent and non-identifying output.

### Profile Collector

Interface:

```ts
readGenerationProfile(formState): GenerationProfile
```

Responsibilities:

- Normalize player answers.
- Enforce max lengths.
- Turn free text into Visible Trait tags.

Keep out:

- Stat math.
- Prompt construction.
- Storage.

### Character Generator

Interface:

```ts
generateCharacter(input): CharacterSpec
```

Input:

```ts
{
  analysis: PhotoAnalysis;
  profile: GenerationProfile;
  reroll: number;
}
```

Responsibilities:

- Select Archetype and Element.
- Choose Rarity.
- Calculate Stats.
- Generate Traits, Skills, Appearance, Personality, and Combat Role.
- Stay deterministic for the same input.

This should become the deepest module first. It hides the most game logic behind one small interface.

### Visual Generator

Interface:

```ts
generateVisuals(input): Promise<GeneratedVisuals>
```

Input:

```ts
{
  sourcePhoto: SourcePhoto;
  character: CharacterSpec;
  mode: "local" | "ai";
}
```

Responsibilities:

- Build the image prompt.
- Call the selected visual adapter.
- Produce Retouched Portrait.
- Render Card Cover.
- Report fallback or model errors.
- Preserve consenting subject likeness while avoiding identity verification claims.

Adapters:

- Local Canvas adapter.
- AI Image Edit adapter.

The seam belongs at `generateVisuals`, not inside UI event handlers.

### Character Library

Interface:

```ts
listBattleCards(): BattleCard[]
saveBattleCard(card): BattleCard
updateBattleCardProgress(id, patch): BattleCard
```

Responsibilities:

- Store saved Battle Cards.
- Preserve schema version.
- Keep progression state separate from generation inputs.

Privacy correction for the next pass:

- The saved Battle Card should not require raw Source Photo storage.
- Store Card Cover and Character Spec by default.
- Keep Source Photo only when the player explicitly opts in.

### Battle Simulator

Interface:

```ts
startBattle(playerCard): BattleState
resolvePlayerAction(state, action): BattleState
```

Responsibilities:

- Convert a Battle Card into a fighter.
- Resolve attack, skill, guard, enemy action, win/loss, and XP.
- Avoid reading photo, UI, storage, or visual generation.

## First Decoupling Pass

The current MVP can stay browser-first, but the next code split should be:

```text
app.js
  -> owns DOM wiring and screen state only

src/photo-analysis.js
  -> analyzePhoto

src/generation-profile.js
  -> read/normalize profile data

src/character-generator.js
  -> generateCharacter

src/visual-generator.js
  -> generateVisuals

src/card-library.js
  -> save/list/update Battle Cards

src/battle-simulator.js
  -> start and resolve battles

server.mjs
  -> static hosting and AI image adapter proxy
```

The first extraction should be `character-generator.js` because it has the highest leverage: tests can verify generated stats, traits, skills, and roles without touching DOM, canvas, storage, camera, or network.

## Quality Rules

- Same inputs plus same reroll produce the same Character Spec.
- AI failure never blocks local preview generation.
- Battle Test never depends on Source Photo or image generation.
- Saved Battle Cards are schema-versioned.
- Prompts must preserve creative intent but avoid identity-recognition claims.
- Visible Traits can affect stats and skills, but should not infer sensitive attributes.
- Sensitive creative context can affect fiction and mechanics only when explicitly supplied with consent.
- Capture Context can affect origin, visuals, element bias, skill flavor, and encounter modifiers, but must have a default fallback.
- Battle Cards must expose visible combat stats generated from allowed photo and user inputs through deterministic rules.
- Rarity should feel exciting but should not be presented as judging the real person.

## Test Targets

1. `analyzePhoto` returns normalized metrics in `0..1`.
2. `readGenerationProfile` trims unsafe and oversized text.
3. `generateCharacter` is deterministic.
4. Combat Style modifies the intended primary stat.
5. Real-World Role rules add expected motifs without replacing Archetype.
6. `generateVisuals` falls back to local visuals when AI fails.
7. `startBattle` and `resolvePlayerAction` work without any photo data.
8. Saving and loading a Battle Card preserves schema, level, XP, wins, and losses.

## Open Decisions

- Which real OCR adapter to use for local MVP.
- Whether Source Photo can ever be stored, and under what explicit consent.
- Whether generated cards should be deterministic forever or tied to generator version.
- Whether future battles are client-only, server-verified, or fully server-authoritative.
- Whether progression belongs on the Battle Card itself or in a separate player-owned progression record.
- How much the AI-generated Retouched Portrait should influence stats, if at all.
- Whether location/time should be collected from device APIs, entered manually, or disabled by default.
